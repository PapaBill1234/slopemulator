# Card ld381-1: LobbyDaemon 381 packets and logic changes against the 2019 + PDB specs

## Goal
You find every difference between LobbyDaemon 381 (the target) and the LobbyDaemon specs, which take their logic from the 2019 + PDB build. You write the 381 command tables, the 381 packet formats and the list of logic changes. You also write the Rust card `Docs/Plan/cards/ld381-1-rust.md`.

## Source rule (user decision, 2026-11-12)
| What | Source | Why |
| --- | --- | --- |
| Logic: jobs, checks, order of steps, database calls, timers | 2019 + PDB build (full names and types) | Readable; the specs `13` to `21` already use it |
| Packets: command ids, handler table flags, formats, field order and sizes, reply codes | 381 build | The 381 client is the target. The client must accept every byte. |
| 381 logic that differs from 2019 and the client can see it | 381 build | 381 wins over 2019 for client-visible behaviour |

## Context
- The target is `BnS_2020/LobbyDaemon` build 381.775 (the BNSX server set). Build 307.643 (`BnS_2020-replaced/LobbyDaemon_307.643`) was the old target. The existing specs give 307 addresses; their logic comes from 2019 + PDB (`22-compare-307.md`).
- The 381 IDB has names that were moved from 2019 + PDB. Each moved name has a comment that starts with `port:` or `port2020:` with the evidence. A comment with ❓ marks a weak name. Check a ❓ name before you use it.
- 381 uses another compiler (VS2019; 2019 uses VS2010). Compare behaviour: strings, callees, constants, formats. Do not compare bytes.
- Compare method and limits: `22-compare-307.md` §1, tools in `tools/ld_match/`.
- LobbyGate is the same build in the old and new server set.

## Work
1. In 381, find the 5 handler tables (manage, LobbyGate, InfoGate, game, account inventory) and the NP (Sts) dispatch. For each row: command, official name, handler address, channel and fragment flags, packet formats. Write `Docs/Server/LobbyDaemon/command-tables-381.json` with the layout of `command-tables.json` and `"target_build": "0.0.381"`.
2. List the commands that are new, removed or moved in 381. List each format that is not the same as in the 307 table.
3. Pair each 381 handler and job class (`12-job-map.md`) with its 2019 + PDB function. Compare strings, callees, constants and formats. Record only the pairs that differ.
4. Compare the config keys and defaults, the gamed link messages and formats, and the database procedure names and parameters.
5. For each difference: 381 address, 2019 + PDB name, what changed, the spec file and section to change, and the effect: `client-visible`, `link`, `db` or `internal`. Apply the source rule.
6. The existing Rust code follows build 307. For each 307 difference in `22-compare-307.md` (§2 to §7) and in `11-character-select.md` §15 (307 addresses): find the 381 behaviour. Write a table "307 rule in the Rust code → 381 rule" with the effect. Find the Rust tests with fixed client bytes: `rg -l "0x[0-9a-f]{2}, 0x" Program/Server/LobbyDaemon Program/Server/LobbyGate`. List each test whose bytes come from a 307 format that changed in 381.
7. Write `Docs/Server/LobbyDaemon/fn-map-381.json`: 2019 + PDB name → 381 address for all verified pairs.
8. Write `Docs/Server/LobbyDaemon/24-compare-381.md`: §1 source rule, method, counts; §2 tables and formats; §3 handler and job changes; §4 config; §5 gamed link; §6 database; §7 new in 381; §8 307 rules in the Rust code and tests with 307 bytes (step 6); §9 open ❓.
9. Write `Docs/Plan/cards/ld381-1-rust.md` (crate `lobbydaemon`; add `packet-ids` if command ids change). It covers the effects `client-visible`, `link` and `db`, every 307 rule in the Rust code that 381 changes, and every test with 307 bytes (update the bytes to 381; keep the test name). Copy the source rule and the architecture rules below into it. It contains the line `cargo test -p lobbydaemon` and a "## Files" list.
